# Data Model

PostgreSQL 16. All migrations via Alembic. All timestamps stored as
`timestamptz`; the frontend renders them in Asia/Tashkent (UTC+5). Calendar
days ("today", date ranges) are Tashkent days (see `DECISIONS.md` D4).

Append-only journal of card opens (D27); a trigger rejects UPDATE and DELETE.
A repeat open of the same card by the same user within 10 minutes is not written.

### audit_log
| column | type | notes |
|--------|------|-------|
| id | bigserial PK | |
| entity | varchar(40) not null | 'property', 'media', 'user', 'district' |
| entity_id | uuid nullable | null only for a failed login with an unknown username |
| action | enum(create, update, delete, restore, login, login_failed, logout) not null | |
| field | varchar(64) nullable | null for delete/restore/login/logout |
| old_value | text nullable | |
| new_value | text nullable | |
| user_id | uuid FK users.id nullable | acting user; null for `login_failed` and for CLI seeding |
| ip | inet nullable | |
| created_at | timestamptz not null default now() | |

One row per changed field. Updating three fields writes three rows within the
same transaction as the update itself. Creating a record writes one row per
populated field with `old_value = NULL`. Password changes are written as field
`password` with both values `NULL`.

`audit_log` is append-only. No UPDATE or DELETE statements against it anywhere
in the codebase; a database trigger rejects them.

## Indexes

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_props_active         ON properties (is_deleted, created_at DESC);
CREATE INDEX idx_props_district       ON properties (district_id) WHERE is_deleted = false;
CREATE INDEX idx_props_created_by     ON properties (created_by) WHERE is_deleted = false;
CREATE INDEX idx_props_status         ON properties (interest_status) WHERE is_deleted = false;
CREATE INDEX idx_props_phone_digits   ON properties (owner_phone_digits);
CREATE INDEX idx_props_phone_trgm     ON properties USING gin (owner_phone_digits gin_trgm_ops);
CREATE INDEX idx_props_request_no     ON properties (request_no);
CREATE INDEX idx_props_request_trgm   ON properties USING gin (request_no gin_trgm_ops);
CREATE INDEX idx_props_landmark_trgm  ON properties USING gin (landmark gin_trgm_ops);
CREATE INDEX idx_props_occupied       ON properties (occupied_until) WHERE is_deleted = false;
CREATE INDEX idx_media_property       ON property_media (property_id, sort_order) WHERE is_deleted = false;
CREATE INDEX idx_audit_entity         ON audit_log (entity, entity_id, created_at DESC);
CREATE INDEX idx_audit_user           ON audit_log (user_id, created_at DESC);
CREATE INDEX idx_auth_sessions_user   ON auth_sessions (user_id);
CREATE INDEX idx_views_user           ON property_views (user_id, viewed_at DESC);
CREATE INDEX idx_views_property       ON property_views (property_id, viewed_at DESC);
CREATE INDEX idx_views_time           ON property_views (viewed_at DESC);
```

The trigram indexes on `owner_phone_digits` and `request_no` serve the
substring matches in search (`LIKE '%…%'` cannot use a b-tree).

## Invariants

1. A property is never hard-deleted. `is_deleted = true` only. A trigger rejects
   `DELETE FROM properties`.
2. Every mutation of `properties` writes at least one `audit_log` row in the
   same transaction. If the audit write fails, the mutation rolls back.
3. `updated_by` and `updated_at` are set by the service layer, never by the
   client payload.
4. An `agent` may only update or soft-delete rows where
   `created_by = current_user.id`. `head` and `admin` have no such restriction.
5. `occupied_until >= today` means the property is currently occupied.
   Availability is derived, never stored as a separate flag.
6. Deactivated users keep all their historical references; their rows are never
   removed.

## Seeding

The first `admin` account is created by a CLI command
(`python -m app.cli create-admin`), never through a public endpoint.
Districts are seeded from a configurable list of Tashkent districts
(`python -m app.cli seed-districts [--file path]`).
